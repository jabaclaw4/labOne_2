## Логика работы `UnqPtr<T>`

`UnqPtr<T>` — единоличный владелец объекта. Внутри хранит только один сырой указатель `T* ptr`.

- Копирование запрещено (`= delete`) — у объекта в памяти всегда ровно один владелец, что исключает двойное удаление.
- Разрешено только перемещение (move) — при передаче `UnqPtr` из одного места в другое `ptr` забирается новым владельцем, а у старого обнуляется. Деструктор пустого `UnqPtr` вызывает `delete nullptr`, что безопасно и ничего не делает.
- Деструктор вызывает `delete ptr` — объект освобождается автоматически, когда `UnqPtr` выходит из области видимости (идиома RAII).
- Подтипизация: шаблонный конвертирующий move-конструктор (ограниченный через `requires std::is_convertible_v<U*, T*>`) позволяет создавать `UnqPtr<Base>` из `UnqPtr<Derived>`, если `Derived` — наследник `Base`.
- `release()` отдаёт указатель наружу без удаления объекта; `reset()` заменяет объект новым, удаляя старый; `get()` только читает адрес без каких-либо побочных эффектов.

`UnqPtr` ничего не знает о существовании `ShrdPtr` или счётчика ссылок — это сознательное разделение ответственности: `UnqPtr` отвечает только за владение и освобождение объекта.

## Логика работы `ShrdPtr<T>`

`ShrdPtr<T>` — разделяемый доступ к объекту. По условию задания не хранит `T*` напрямую, а хранит указатель `master` на `UnqPtr<T>`, через который и добирается до объекта (`master->get()`).

Счётчик ссылок (`size_t* referenceCount`) полностью в ведении `ShrdPtr`:
- При копировании `ShrdPtr` счётчик увеличивается — появился новый реальный держатель ссылки.
- При перемещении (move) счётчик не меняется — владелец не размножился, просто переехал в другой объект в памяти.
- При уничтожении `ShrdPtr` (или присваивании ему нового значения) счётчик уменьшается; когда он доходит до нуля — память под сам счётчик освобождается.

`ShrdPtr` можно создать двумя способами:
1. От уже существующего `UnqPtr&` — `ShrdPtr` не владеет этим `UnqPtr`, только ссылается на него.
2. От сырого указателя `T*` — конструктор сам создаёт `UnqPtr` внутри и берёт на себя ответственность за его удаление, когда счётчик дойдёт до нуля (отслеживается флагом `ownsMaster`).

Подтипизация реализована аналогично `UnqPtr` — конвертирующий copy-конструктор с `requires`, внутри использующий `reinterpret_cast` для приведения `master` между разными специализациями `UnqPtr<T>` (безопасно за счёт одинаковой раскладки памяти всех специализаций).

## Нагрузочные тесты — методика

`load_test.cpp` замеряет:
- **Время** — через `<chrono>`, медиана из 5 прогонов с предварительным прогревом аллокатора памяти (иначе первый измеряемый вариант несправедливо "платит" за инициализацию страниц памяти операционной системой).
- **Память** — аналитически через `sizeof()` (размер обёртки × количество элементов), а не через рантайм-трекинг — это избегает риска, связанного с перегрузкой глобального `operator new`.
- **Диапазон N** — 10, 100, 1000 (малые объёмы), 100 000, 1 000 000, 10 000 000 (большие объёмы) — по требованию задания.
- **Сравнение** — сырой `new`/`delete`, `UnqPtr`, `std::unique_ptr` (опциональное сравнение со STL).

### Интерпретация результатов

**По времени:** все три варианта показывают сопоставимое, близкое по порядку величины время на всех N. Наблюдаемое систематическое преимущество `UnqPtr` перед `raw new/delete` на каждом N — не характеристика архитектуры, а эффект методологии измерения: варианты запускаются последовательно в одном процессе, и более ранний в очереди вариант "платит" за первичный прогрев страниц памяти операционной системой сильнее последующих. Содержательный вывод: сама стоимость выделения памяти через `new` доминирует над накладными расходами обёртки указателя, разница между вариантами на этом фоне мала.

**По памяти:** разница чёткая и стабильная — `UnqPtr` в 2 раза "тяжелее" по размеру обёртки (16 байт против 8), потому что резервирует место под указатель на объект и обеспечивает основу для будущей связи со счётчиком ссылок через `ShrdPtr`.

**Масштабируемость:** время растёт линейно от N во всех вариантах (подтверждается на графике в логарифмических осях прямой линией) — ни собственная реализация, ни STL не вносят алгоритмической деградации при увеличении числа объектов.

## Проверка памяти: AddressSanitizer + UndefinedBehaviorSanitizer

Так как valgrind не работает нативно на Windows, для оперативной проверки использованы встроенные в компилятор санитайзеры.

**Настройка в `CMakeLists.txt`:**
```cmake
option(ENABLE_SANITIZERS "Enable AddressSanitizer and UBSan" OFF)

if(ENABLE_SANITIZERS)
    add_compile_options(-fsanitize=address,undefined -g -fno-omit-frame-pointer)
    add_link_options(-fsanitize=address,undefined)
endif()
```

**Профиль сборки в CLion:**
- Build type: `Debug` (без оптимизаций — иначе отчёты санитайзера неточны)
- CMake options: `-DENABLE_SANITIZERS=ON`
- Toolchain: MinGW (встроенный в CLion)

**Что проверяется:** use-after-free, double-free, выход за границы буфера (AddressSanitizer), неопределённое поведение (UndefinedBehaviorSanitizer). LeakSanitizer на MinGW/Windows работает нестабильно — для утечек основным инструментом стал valgrind (см. ниже).

**Прогон:** сборка с этим профилем, запуск программы через меню (пункт 1 — функциональные тесты). Отсутствие вывода от санитайзера при нормальном завершении программы означает отсутствие обнаруженных ошибок памяти. Работа санитайзера дополнительно проверена вручную — временно внесённая ошибка (use-after-free) корректно обнаруживалась и прерывала выполнение с точным указанием строки.

## Известные ограничения реализации

- Конвертирующий конструктор `ShrdPtr` использует `reinterpret_cast` для приведения `UnqPtr<U>*` к `UnqPtr<T>*` — безопасно только за счёт одинаковой раскладки в памяти всех специализаций `UnqPtr<T>`.
- Два независимых `ShrdPtr`, созданных от одного и того же `UnqPtr&` через разные вызовы конструктора (а не через копирование одного `ShrdPtr`), заводят независимые счётчики ссылок.
- `DynamicArray::Grow()` физически переносит ячейки `UnqPtr` на новый адрес в памяти при расширении — `ShrdPtr`, полученный через `Share()` до вызова `Grow()`, может стать некорректным после последующего расширения массива.
